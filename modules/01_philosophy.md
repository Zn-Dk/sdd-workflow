# 01. 核心理念

## SDD 原则

规范驱动开发（Spec-Driven Development）的核心：**先明确"做什么"，再决定"怎么做"**。

### 六大原则

| #   | 原则                | 说明                                     | 来源          |
| --- | ------------------- | ---------------------------------------- | ------------- |
| 1   | **SPEC 为第一准则** | 需求方向调整必须先改 SPEC，再改代码      | 实战经验      |
| 2   | **变更必留痕**      | 每次迭代记录 changelog，含根因分析       | 实战经验      |
| 3   | **文件归属约束**    | 所有 agent 记录文件集中在需求 \_dev 目录 | 实战经验      |
| 4   | **外科手术式修改**  | 最小改动、只改必须改的、不顺手重构       | Karpathy 准则 |
| 5   | **验证闭环**        | 修复后必须验证不引入回归                 | 实战经验      |
| 6   | **渐进式实施**      | 分阶段交付，每阶段有明确验收标准         | 实战经验      |

### 与 Karpathy 准则的关系

SDD 在**流程层**引用 Karpathy 准则作为**行为层**约束：

```
SDD（流程层）
  ├── 需求分析 → "先思考再编码"
  ├── 代码实施 → "最小改动 + 外科手术式修改"
  ├── Bug 修复 → "定义可验证的成功标准"
  └── 全程 → "表面化假设，不隐藏困惑"
```

## 文件职责矩阵

每个文件有且只有一个核心职责，避免职责混淆：

| 文件              | 核心职责                             | 写入时机                     | 大小控制           |
| ----------------- | ------------------------------------ | ---------------------------- | ------------------ |
| `SPEC.md`         | **需求规格** — 描述"做什么 + 为什么" | 需求初期创建，方向调整时修改 | 无上限，但保持聚焦 |
| `CLAUDE.md`       | **约束记录** — 只记录 MARK 指令      | 用户发出硬性规则时追加       | ≤ 20 条 MARK       |
| `PLAN.md`         | **阶段规划** — Phase 划分 + 验收标准 | 需求初期创建，阶段完成后标记 | ≤ 3KB              |
| `DECISIONS.md`    | **架构决策** — ADR 格式，记录取舍    | 遇到技术分歧时追加           | 每条 ≤ 500 字      |
| `changelog.md`    | **变更日志** — 每次迭代的完整记录    | 每次迭代追加                 | 无上限，有密度要求 |
| `TODO.md`         | **待办事项** — 已知但暂不修的问题    | 发现问题但不立即处理时       | 按条目增长         |
| `DESIGN_GUIDE.md` | **设计稿分析** — 视觉/交互参考       | 有设计稿时创建               | 按需               |

### 职责边界判断

遇到"该写在哪里"的困惑时，使用以下决策树：

```
这条信息是什么？
├── "必须遵守的规则" → CLAUDE.md（MARK）
├── "为什么选方案 A 不选 B" → DECISIONS.md
├── "这次改了什么 + 为什么" → changelog.md
├── "接下来要做什么" → TODO.md 或 Agent task_list
├── "需求是什么" → SPEC.md
├── "什么算做完" → PLAN.md（验收标准）
└── "设计稿怎么说" → DESIGN_GUIDE.md
```

## 反模式

❌ SPEC 没改就开始写代码（方向偏离后返工成本极高）
❌ 修复 Bug 时顺手重构不相关代码（Bug 71→72 的教训）
❌ changelog 只记"改了什么"不记"为什么"（后续无法追溯决策）
❌ 实验性代码没有标注就合入（后续不知道该保留还是回滚）
❌ CLAUDE.md 什么都往里塞（应该只有 MARK 约束）
❌ PLAN.md 记录实施细节（应该只有 Phase + 验收标准）
