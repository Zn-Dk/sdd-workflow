# 03. 产出物规范

## 目录结构

每个需求开发在对应模块下创建 `_dev/` 目录：

```
<project-root>/<module-path>/_<feature>_dev/
├── SPEC.md              # 需求规格（第一准则）
├── CLAUDE.md            # MARK 约束记录
├── PLAN.md              # 阶段规划（≤ 3KB）
├── DECISIONS.md         # 架构决策（可选）
├── changelog.md         # 变更日志
├── TODO.md              # 待办事项
└── DESIGN_GUIDE.md      # 设计稿分析（可选）
```

---

## 各文件详细规范

### SPEC.md — 需求规格

**职责**：描述"做什么 + 为什么"，是开发的第一准则。

**结构要求**：

```markdown
> ⚠️ 关键约束摘要（≤ 5 行，最容易被遗忘的核心约束）

# 功能名称

## 1. 概述

## 2. 功能需求

## 3. 交互规范

## 4. 实施阶段（可选，大需求时使用）

## 5. 验收标准
```

**写入规则**：

- 只描述 What + Why，不描述 How
- 方向调整时必须先改 SPEC，再改代码
- 变更使用标记：`[NEW]` / `[CHANGED]` / `[REMOVED]`

**反模式**：

- ❌ 混入实施细节（如"用 computed 实现"）
- ❌ 方向变了但 SPEC 没更新

---

### CLAUDE.md — 约束记录

**职责**：只记录 MARK 指令（用户发出的硬性规则）。

**结构要求**：

```markdown
## ⚡ 高频约束（每次迭代必看）

1. [最重要的约束]
2. [第二重要的约束]
   ...（≤ 5 条）

## MARK 记录

### MARK #1: [标题]

- 内容：[具体约束]
- 来源：[用户在哪次对话中提出]
- 状态：生效 / 已废弃

### MARK #2: [标题]

...
```

**写入规则**：

- 只有用户明确发出的硬性规则才记录为 MARK
- 总数不超过 20 条
- 废弃的 MARK 标记状态但不删除（保留追溯）

**反模式**：

- ❌ 把实施细节、Bug 分析、设计方案写进来
- ❌ Agent 自己决定的规则记为 MARK（必须是用户发出的）

---

### PLAN.md — 阶段规划

**职责**：Phase 划分 + 验收标准，只回答"做什么 + 什么算做完"。

**结构要求**：

```markdown
# 需求实施计划

## Phase 1: [阶段名] [状态: ✅/🔄/⏳]

- 验收标准: [具体可验证的标准]
- 涉及模块: [文件/模块列表]
- 已知风险: [可选]

## Phase 2: [阶段名] [状态]

...
```

**写入规则**：

- 总大小 ≤ 3KB
- 不记录"怎么做"（实施细节由 Agent task_list 管理）
- 阶段完成后标记 ✅

**反模式**：

- ❌ 记录实施步骤细节（应在 Agent task_list 中）
- ❌ 记录技术方案分析（应在 DECISIONS.md 中）
- ❌ 记录 Bug 分析（应在 changelog.md 中）

---

### DECISIONS.md — 架构决策

**职责**：ADR 格式，记录"为什么选方案 A 不选 B"。

**结构要求**：使用 [assets/decision-template.md](../assets/decision-template.md) 模板。

**写入规则**：

- 每条决策 ≤ 500 字
- 遇到技术分歧时追加
- 废弃的决策标记 `[SUPERSEDED]` 但不删除

**反模式**：

- ❌ 记录实施细节
- ❌ 不记录"考虑过的替代方案"

---

### changelog.md — 变更日志

**职责**：每次迭代的完整记录，含根因分析。

**结构要求**：

````markdown
## 快速索引

| 编号    | 类型 | 标题   |
| ------- | ---- | ------ |
| Bug 72  | Bug  | [标题] |
| 重构 45 | 重构 | [标题] |

## 正文

### Bug 72: [标题]

**问题描述**：[现象]
**根因分析**：[≤ 5 行，解释为什么出问题]
**修复方案**：[做了什么]
**修改文件**：

| 文件    | 改动说明   |
| ------- | ---------- |
| xxx.vue | [具体改动] |

**核心改动**：

```code
[关键代码片段]
```
````

````

**写入规则**：
- 每次迭代必须追加
- 根因分析 ≤ 5 行（密度要求）
- Bug 编号递增，重构编号递增
- 索引表同步更新

**反模式**：
- ❌ 只记"改了什么"不记"为什么"
- ❌ 根因分析写成长篇论文
- ❌ 忘记更新索引表

---

### TODO.md — 待办事项

**职责**：记录"已知但暂不修"的问题。

**结构要求**：

```markdown
# 待办事项

## 高优先级
- [ ] [描述] — 来源：[Bug/需求/Review]

## 低优先级
- [ ] [描述] — 来源：[Bug/需求/Review]

## 已完成
- [x] [描述] — 完成于：[日期]
````

**写入规则**：

- 发现问题但不立即处理时记录
- 完成后移到"已完成"区域（不删除，保留追溯）

---

## 内容归属速查

| 原来可能写在 PLAN.md 的内容 | 应该去哪里                    |
| --------------------------- | ----------------------------- |
| Phase 划分 + 验收标准       | 留在 PLAN.md                  |
| 技术方案分析                | → DECISIONS.md                |
| 实施步骤细节                | → Agent task_list（不持久化） |
| Bug 分析                    | → changelog.md                |
| 现有组件适配性分析          | → DECISIONS.md                |
| 代码结构设计                | → SPEC.md 或 DECISIONS.md     |
