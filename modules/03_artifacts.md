# 03. 产出物规范

## 目录结构

每个模块下统一建**一个** `_dev/` 目录，模块内的每个需求/迭代/修复各占一个子目录（`_dev/<type>_<slug>`），共享同一命名空间：

```
src/components/v3/rule-engine/_dev/
├── feat_parallel-node/       # 新功能 A
│   ├── SPEC.md               # 需求规格（第一准则）
│   ├── CLAUDE.md             # MARK 约束记录
│   ├── PLAN.md               # 阶段规划（≤ 3KB）
│   ├── DECISIONS.md          # 架构决策（可选）
│   ├── changelog.md          # 变更日志
│   ├── TODO.md               # 待办事项
│   ├── DESIGN_GUIDE.md       # 设计稿分析（可选）
│   ├── findings.md           # 研究发现（会话级，可选）
│   └── progress.md           # 会话日志（会话级，可选）
├── perf_strategy-lazyload/   # 性能优化 B（同模块下一迭代）
└── fix_export-crash/         # 修复 C
```

> ⚠️ `findings.md` 和 `progress.md` 是会话级文件（Agent 工作记忆），不是交付物。可在 `.gitignore` 中排除。其使用规范参见 [06_session-persistence.md](06_session-persistence.md)。

> **命名规范**：`<type>_<slug>`
> - `type`：复用项目 commitlint 提交类型（`feat` / `fix` / `refactor` / `perf` …），下划线 `_` 作为 type 与 slug 的主分隔。
> - `slug`：kebab-case、名词化、≤ 3-4 词；因已嵌套在模块 `_dev/` 下，无需再带模块前缀。
> - 不强制编号 / 日期（git 已提供时间轴，编号在并行分支易冲突）；同一 feature 多轮并存时用 `-vN` 后缀区分。

---

## 文件更新触发矩阵

| 变化类型 | 必须更新的文件 | 说明 |
|---------|---------------|------|
| 需求新增 / 修改 / 删除 | `SPEC.md` | 方向变化先改 SPEC |
| 阶段推进 / 验收标准变化 | `PLAN.md` | 保持 Phase 状态与验收标准一致 |
| 用户新增硬约束 | `CLAUDE.md` | 只记录用户明确给出的规则 |
| 技术方案取舍变化 | `DECISIONS.md` | 记录为什么选 A 不选 B |
| 任意代码实施 / 修复 / 重构 | `changelog.md` | 每轮代码变更都要留痕 |
| 已知问题暂不处理 | `TODO.md` | 避免问题只停留在对话里 |

## 各文件详细规范

### SPEC.md — 需求规格

**职责**：描述"做什么 + 为什么"，是开发的第一准则。

**结构要求**：

```markdown
> ⚠️ 关键约束摘要（≤ 5 行，最容易被遗忘的核心约束）

# 功能名称

## 1. 概述
## 2. 功能需求
## 3. 交互规范
## 4. 实施阶段（可选，大需求时使用）
## 5. 验收标准
```

**写入规则**：
- 只描述 What + Why，不描述 How
- 方向调整时必须先改 SPEC，再改代码
- 变更使用标记：`[NEW]` / `[CHANGED]` / `[REMOVED]`
- 出现需求新增、需求语义变化、需求删除时必须同步更新

**反模式**：
- ❌ 混入实施细节（如"用 computed 实现"）
- ❌ 方向变了但 SPEC 没更新

---

### CLAUDE.md — 约束记录

**职责**：只记录 MARK 指令（用户发出的硬性规则）。

**结构要求**：

```markdown
## ⚡ 高频约束（每次迭代必看）

1. [最重要的约束]
2. [第二重要的约束]
...（≤ 5 条）

## MARK 记录

### MARK #1: [标题]
- 内容：[具体约束]
- 来源：[用户在哪次对话中提出]
- 状态：生效 / 已废弃

### MARK #2: [标题]
...
```

**写入规则**：
- 只有用户明确发出的硬性规则才记录为 MARK
- 总数不超过 20 条
- 废弃的 MARK 标记状态但不删除（保留追溯）
- 用户新增、修正、废弃硬约束时必须同步更新

**反模式**：
- ❌ 把实施细节、Bug 分析、设计方案写进来
- ❌ Agent 自己决定的规则记为 MARK（必须是用户发出的）

---

### PLAN.md — 阶段规划

**职责**：Phase 划分 + 验收标准，只回答"做什么 + 什么算做完"。

**结构要求**：

```markdown
# 需求实施计划

## Phase 1: [阶段名] [状态: ✅/🔄/⏳]
- 验收标准: [具体可验证的标准]
- 涉及模块: [文件/模块列表]
- 已知风险: [可选]

## Phase 2: [阶段名] [状态]
...
```

**写入规则**：
- 总大小 ≤ 3KB
- 不记录"怎么做"（实施细节由 Agent task_list 管理）
- 阶段完成后标记 ✅
- 阶段状态、阶段划分、验收标准变化时必须同步更新

**反模式**：
- ❌ 记录实施步骤细节（应在 Agent task_list 中）
- ❌ 记录技术方案分析（应在 DECISIONS.md 中）
- ❌ 记录 Bug 分析（应在 changelog.md 中）

---

### DECISIONS.md — 架构决策

**职责**：ADR 格式，记录"为什么选方案 A 不选 B"。

**结构要求**：使用 [assets/decision-template.md](../assets/decision-template.md) 模板。

**写入规则**：
- 每条决策 ≤ 500 字
- 遇到技术分歧时追加
- 废弃的决策标记 `[SUPERSEDED]` 但不删除
- 技术取舍发生变化时必须追加或更新对应决策

**反模式**：
- ❌ 记录实施细节
- ❌ 不记录"考虑过的替代方案"

---

### changelog.md — 变更日志

**职责**：每次迭代的完整记录，含根因分析。

**结构要求**：

```markdown
## 快速索引

| 编号 | 类型 | 标题 |
|------|------|------|
| Bug 72 | Bug | [标题] |
| 重构 45 | 重构 | [标题] |

## 正文

### Bug 72: [标题]

**问题描述**：[现象]
**根因分析**：[≤ 5 行，解释为什么出问题]
**修复方案**：[做了什么]
**修改文件**：

| 文件 | 改动说明 |
|------|---------|
| xxx.vue | [具体改动] |

**核心改动**：
```code
[关键代码片段]
```
```

**写入规则**：
- 每次迭代必须追加
- 根因分析 ≤ 5 行（密度要求）
- Bug 编号递增，重构编号递增
- 索引表同步更新
- 任意代码实施、Bug 修复、Review 后修正都必须记录

**反模式**：
- ❌ 只记"改了什么"不记"为什么"
- ❌ 根因分析写成长篇论文
- ❌ 忘记更新索引表

---

### TODO.md — 待办事项

**职责**：记录"已知但暂不修"的问题。

**结构要求**：

```markdown
# 待办事项

## 高优先级
- [ ] [描述] — 来源：[Bug/需求/Review]

## 低优先级
- [ ] [描述] — 来源：[Bug/需求/Review]

## 已完成
- [x] [描述] — 完成于：[日期]
```

**写入规则**：
- 发现问题但不立即处理时记录
- 完成后移到"已完成"区域（不删除，保留追溯）
- 明确决定暂不处理的问题必须落到 TODO.md，而不是只写在回复里

## 内容归属速查

| 原来可能写在 PLAN.md 的内容 | 应该去哪里 |
|---------------------------|-----------|
| Phase 划分 + 验收标准 | 留在 PLAN.md |
| 技术方案分析 | → DECISIONS.md |
| 实施步骤细节 | → Agent task_list（不持久化） |
| Bug 分析 | → changelog.md |
| 现有组件适配性分析 | → DECISIONS.md |
| 代码结构设计 | → SPEC.md 或 DECISIONS.md |
| 源码阅读笔记 / 调研发现 | → findings.md（会话级，参见 06） |
| 会话工作轨迹 | → progress.md（会话级，参见 06） |

---

## 反模式补充

- ❌ 把 `_dev` 文件当作最后统一补写的归档动作，而不是跟随每轮状态变化即时同步
- ❌ 已经判断出 dirty 文件，却把同步留到下一轮"顺手再补"
- ❌ 把会话级文件（findings.md / progress.md）当作产出物提交到 git（它们是 Agent 工作记忆，可 .gitignore）
- ❌ 把产出物内容复制到会话级文件（信息冗余，违反单一数据源原则）
