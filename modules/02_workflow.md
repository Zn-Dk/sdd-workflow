# 02. 开发工作流

## 阶段总览

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│ 需求分析 │ → │ 架构设计 │ → │ 代码实施 │ → │ 质量验证 │ → │ 迭代修复 │
│         │    │         │    │         │    │         │    │         │
│spec-    │    │ 自身规范 │    │code-    │    │code-    │    │ 自身协议 │
│writing  │    │         │    │generate │    │review   │    │         │
└─────────┘    └─────────┘    └─────────┘    └─────────┘    └─────────┘
```

---

## 阶段 1：需求分析

**触发**：用户提出新功能需求或需求变更
**引用**：`spec-writing` skill

### 产出物

| 文件            | 必须/可选 | 说明                            |
| --------------- | --------- | ------------------------------- |
| SPEC.md         | 必须      | 需求规格，描述"做什么 + 为什么" |
| DESIGN_GUIDE.md | 可选      | 有设计稿时，分析视觉/交互参考   |

### 执行要点

1. 调用 `spec-writing` skill 生成 SPEC.md
2. SPEC 顶部添加「关键约束摘要」（≤ 5 行 blockquote）
3. 如有设计稿，生成 DESIGN_GUIDE.md
4. 与用户确认 SPEC 内容后才进入下一阶段

### SPEC 变更标记约定

当 SPEC 内容发生变更时，使用以下标记：

- `[NEW]` — 新增需求
- `[CHANGED]` — 修改已有需求（附简要说明）
- `[REMOVED]` — 废弃需求（保留删除线，附原因）

---

## 阶段 2：架构设计

**触发**：SPEC 确认后，开始技术方案设计
**引用**：自身规范（03_artifacts.md）

### 产出物

| 文件         | 必须/可选 | 说明                           |
| ------------ | --------- | ------------------------------ |
| PLAN.md      | 必须      | Phase 划分 + 验收标准（≤ 3KB） |
| DECISIONS.md | 可选      | 有技术分歧时，记录 ADR         |

### 执行要点

1. 创建 PLAN.md：只记录 Phase + 验收标准，不记录实施细节
2. 遇到技术选型分歧时，创建/追加 DECISIONS.md
3. 使用 [assets/decision-template.md](../assets/decision-template.md) 模板

---

## 阶段 3：代码实施

**触发**：架构设计完成，开始编码
**引用**：`code-generate` skill（如有）

### 执行要点

1. 调用 `code-generate` skill 执行代码生成（如有该 skill）
2. 每次实施完成后，追加 changelog.md 条目
3. 遵循 Karpathy 准则：最小改动、外科手术式修改
4. 实施过程中发现的问题记录到 TODO.md

---

## 阶段 4：质量验证

**触发**：代码实施完成，需要质量检查
**引用**：`code-review` skill（如有）

### 执行要点

1. 调用 `code-review` skill 执行审查（如有该 skill）
2. 审查发现的问题分类处理：
   - 必须修复 → 立即修复 + 记录 changelog
   - 可以后续优化 → 记录 TODO.md

---

## 阶段 5：迭代修复

**触发**：发现 Bug 或需要调整
**引用**：自身 04_iteration-protocol.md

### 执行要点

1. 按 04_iteration-protocol 的 Bug 修复闭环执行
2. 修复后验证不引入回归
3. 记录 changelog + 必要时更新 DECISIONS.md

---

## 回顾检查点（防遗漏协议）

### 触发条件 → 必须回顾的文件

| 触发条件           | 必须回顾                 | 目的                   |
| ------------------ | ------------------------ | ---------------------- |
| 开始新的迭代/Phase | SPEC.md + CLAUDE.md      | 确认需求方向和硬性约束 |
| 修复 Bug           | changelog.md（相关条目） | 避免重复踩坑           |
| 修改共享模块       | DECISIONS.md             | 确认不违反已有架构决策 |
| 用户说"先试试"     | CLAUDE.md（标记实验性）  | 后续知道要回滚还是固化 |
| 迭代超过 5 轮对话  | CLAUDE.md                | 刷新约束记忆           |

### 回顾格式

Agent 回顾后，在回复中简要确认：

```
📋 已回顾 CLAUDE.md（N 条 MARK），本次修改涉及 MARK #X（描述）、MARK #Y（描述）。
```

---

## 跨模块修改影响评估

当修改涉及多个模块时，必须在实施前做轻量影响评估：

```markdown
## 变更影响评估

- 本次修改涉及哪些文件？
- 哪些已有功能可能受影响？
- 是否需要回归验证？验证什么？
```

---

## 反模式

❌ 跳过需求分析直接写代码
❌ SPEC 未确认就开始架构设计
❌ 代码实施后不记录 changelog
❌ 修改共享模块前不回顾 DECISIONS.md
❌ 迭代超过 5 轮不刷新约束记忆
