# 02. 开发工作流

## 需求规模判断（入口决策）

加载本 skill 后，Agent 首先判断需求规模，决定走哪条路径：

```
需求规模？
├── 热修复（< 10 行改动，单点 Bug）
│   → 直接跳转「阶段 5：迭代修复」
│   → 产出物：changelog.md 条目
│
├── 小需求（单文件/单组件，无架构影响）
│   → 跳过阶段 2（架构设计）
│   → 简化 SPEC（可用 1-2 段文字替代完整模板）
│   → 产出物：简化 SPEC + changelog
│
└── 中大需求（跨模块、新功能、架构变更）
    → 完整 5 阶段流程
    → 产出物：全套 _dev/ 文件
```

**判断依据**：

- 改动文件数 ≤ 1 且行数 < 10 → 热修复
- 改动文件数 ≤ 2 且不涉及新组件/新模块 → 小需求
- 其他 → 中大需求

## 阶段 1：需求分析

**触发**：用户提出新功能需求或需求变更
**前置条件**：无（流程起点）
**引用**：`spec-writing` skill

### 产出物

| 文件            | 必须/可选 | 说明                            |
| --------------- | --------- | ------------------------------- |
| SPEC.md         | 必须      | 需求规格，描述"做什么 + 为什么" |
| DESIGN_GUIDE.md | 可选      | 有设计稿时，分析视觉/交互参考   |

### 执行要点

1. 调用 `spec-writing` skill 生成 SPEC.md
2. SPEC 顶部添加「关键约束摘要」（≤ 5 行 blockquote）
3. 如有设计稿，生成 DESIGN_GUIDE.md
4. 与用户确认 SPEC 内容后才进入下一阶段

### 退出条件（回到编排层）

`spec-writing` 子 skill 执行完毕后，必须回到 SDD 编排层继续阶段 2。退出标志：

- SPEC.md 已生成且用户确认 ✅
- DESIGN_GUIDE.md 已生成（如有设计稿）或确认无需创建

### SPEC 变更标记约定

当 SPEC 内容发生变更时，使用以下标记：

- `[NEW]` — 新增需求
- `[CHANGED]` — 修改已有需求（附简要说明）
- `[REMOVED]` — 废弃需求（保留删除线，附原因）

---

## 阶段 2：架构设计

**触发**：SPEC 确认后，开始技术方案设计
**前置条件**：SPEC.md 已创建且用户已确认 ✅
**引用**：自身规范（03_artifacts.md）

### 产出物

| 文件         | 必须/可选 | 说明                           |
| ------------ | --------- | ------------------------------ |
| PLAN.md      | 必须      | Phase 划分 + 验收标准（≤ 3KB） |
| DECISIONS.md | 可选      | 有技术分歧时，记录 ADR         |

### 执行要点

1. 创建 PLAN.md：只记录 Phase + 验收标准，不记录实施细节
2. 遇到技术选型分歧时，创建/追加 DECISIONS.md
3. 使用 [assets/decision-template.md](../assets/decision-template.md) 模板

---

## 阶段 3：代码实施

**触发**：架构设计完成，开始编码
**前置条件**：PLAN.md 已创建；DECISIONS.md 已记录（如有技术分歧）
**引用**：`code-generate` skill → `knowledge-base`

### 执行要点

1. 调用 `code-generate` skill 执行代码生成
2. 每次实施完成后，先判断 `_dev` dirty-state，再同步对应文件；至少追加 changelog.md 条目
3. 遵循 Karpathy 准则：最小改动、外科手术式修改
4. 实施过程中发现的问题记录到 TODO.md

---

## 阶段 4：质量验证

**触发**：代码实施完成，需要质量检查
**前置条件**：代码实施完成；changelog.md 已追加本次变更条目
**引用**：`code-review` skill

### 执行要点

1. 调用 `code-review` skill 执行审查
2. 审查发现的问题分类处理：
   - 必须修复 → 立即修复 + 记录 changelog
   - 可以后续优化 → 记录 TODO.md

---

## 阶段 5：迭代修复

**触发**：发现 Bug 或需要调整
**前置条件**：Bug 已复现或问题已明确描述
**引用**：自身 04_iteration-protocol.md

### 执行要点

1. 按 04_iteration-protocol 的 Bug 修复闭环执行
2. 修复后验证不引入回归
3. 记录 changelog + 必要时更新 DECISIONS.md

---

## 回顾检查点（防遗漏协议）

### 触发条件 → 必须回顾的文件

| 触发条件           | 必须回顾                                                 | 目的                           |
| ------------------ | -------------------------------------------------------- | ------------------------------ |
| 开始新的迭代/Phase | SPEC.md + CLAUDE.md                                      | 确认需求方向和硬性约束         |
| 修复 Bug           | changelog.md（相关条目）                                 | 避免重复踩坑                   |
| 修改共享模块       | DECISIONS.md                                             | 确认不违反已有架构决策         |
| 用户说"先试试"     | CLAUDE.md（标记实验性）                                  | 后续知道要回滚还是固化         |
| 迭代超过 5 轮对话  | SPEC.md + CLAUDE.md + PLAN.md + changelog.md（最近条目） | 恢复最小上下文，避免长对话漂移 |

### 回顾格式

Agent 回顾后，在回复中简要确认：

```
📋 已回顾 CLAUDE.md（N 条 MARK），本次修改涉及 MARK #X（描述）、MARK #Y（描述）。
```

## 回合级同步协议

### `_dev` dirty-state 判定

| 本轮变化           | 必须同步     | 说明                                   |
| ------------------ | ------------ | -------------------------------------- |
| 修改代码           | changelog.md | 任意实施、修复、重构都要留下本轮记录   |
| 改变需求边界/解释  | SPEC.md      | 方向调整先改 SPEC，再改代码            |
| 推进或调整阶段状态 | PLAN.md      | Phase 状态、验收标准变化都属于计划同步 |
| 新增用户硬约束     | CLAUDE.md    | 只记录用户明确给出的硬规则             |
| 发现暂不处理的问题 | TODO.md      | 已知问题不能只停留在回复里             |
| 改变技术取舍       | DECISIONS.md | 记录为什么改选方案                     |

### 收尾门禁

- 本轮存在 dirty 产物未同步时，不得以"已完成""已修复""已处理完"结束本轮。
- 如果明确判断某个文件本轮无需更新，需要给出简短理由，避免默认遗漏。
- 回顾用于恢复上下文，同步用于更新状态；二者不能互相替代。

### 多轮恢复协议

以下任一满足时，必须执行最小恢复：

- 连续对话超过 5 轮
- 切换过话题后回到原需求
- 重新进入已有 `_dev/` 目录继续实施
- 上一轮已改代码，但未显式确认 `_dev` 已同步
- 新会话开始或 `/clear` 后重新进入需求

#### 恢复步骤

```
Step 1: 检查代码变更
   → git diff --stat（查看自上次以来的代码改动）
   → git log --oneline -5（查看最近提交）

Step 2: 读取会话级文件（如有，参见 06_session-persistence.md）
   → progress.md（上次会话做到哪一步）
   → findings.md（研究阶段发现了什么）

Step 3: 读取 _dev/ 产出物（最小恢复集合）
   → SPEC.md
   → CLAUDE.md
   → PLAN.md
   → changelog.md 最近条目
   → 必要时 TODO.md

Step 4: 对比与修正
   → 代码变更是否已反映在 changelog 中？
   → 阶段状态是否与 PLAN.md 一致？
   → 如有偏差，先同步 _dev/ 产出物，再继续工作
```

> ⚠️ 中大需求或跨会话场景下，会话级文件（`progress.md` / `findings.md`）的创建和使用参见 [06_session-persistence.md](06_session-persistence.md)。小需求可跳过会话级文件，仅执行 Step 1 + Step 3。

## 跨模块修改影响评估

当修改涉及多个模块时，必须在实施前做轻量影响评估：

```markdown
## 变更影响评估

- 本次修改涉及哪些文件？
- 哪些已有功能可能受影响？
- 是否需要回归验证？验证什么？
```

## 反模式

❌ 跳过需求分析直接写代码
❌ SPEC 未确认就开始架构设计
❌ 代码实施后不记录 changelog
❌ 修改共享模块前不回顾 DECISIONS.md
❌ 迭代超过 5 轮不刷新约束记忆
❌ 本轮有 dirty 产物却跨轮悬空
❌ 跨会话恢复时只读 `_dev/` 产出物，不读会话级文件（丢失工作轨迹）
❌ 读了源码/截图/文档后不及时写入 `findings.md`（多模态信息丢失）
