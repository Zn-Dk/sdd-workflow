# 04. 迭代协议

## 概述

迭代协议覆盖开发过程中的四种常见场景：

1. Bug 修复闭环
2. 回归检测
3. 决策回溯
4. 实验性代码管理

---

## 1. Bug 修复闭环

### 标准流程

```
复现 → 根因分析 → 最小修复 → 回归验证 → changelog 记录
```

### 详细步骤

| 步骤        | 动作                           | 产出           |
| ----------- | ------------------------------ | -------------- |
| 1. 复现     | 确认 Bug 现象，明确复现条件    | 复现步骤描述   |
| 2. 根因分析 | 定位问题代码，分析"为什么出错" | 根因（≤ 5 行） |
| 3. 最小修复 | 只改必须改的，不顺手重构       | 代码修改       |
| 4. 回归验证 | 验证修复有效 + 不引入新问题    | 验证结果       |
| 5. 记录     | 追加 changelog 条目            | changelog 更新 |

### 根因分析模板

```markdown
**根因**：[一句话概括]
**详细**：

- 触发条件：[什么情况下触发]
- 代码位置：[文件:行号 或 函数名]
- 错误逻辑：[为什么这段代码会出错]
```

### 反模式

- ❌ 不分析根因直接"试着改改"
- ❌ 修复时顺手重构相邻代码
- ❌ 修复后不验证回归
- ❌ 忘记记录 changelog

---

## 2. 回归检测

### 触发条件

当修复涉及以下情况时，必须执行回归检测：

- 修改了共享函数/工具方法
- 修改了布局/排版算法
- 修改了数据流/状态管理
- 修改了组件的 props/emit 接口

### 检测策略

```
修改了什么？
├── 共享函数 → 搜索所有调用方，逐一验证
├── 布局算法 → 验证所有使用该算法的场景
├── 数据流 → 验证上下游组件的数据正确性
└── 接口变更 → 验证所有父组件的传参
```

### 回归验证清单

```markdown
## 回归验证

- [ ] 修复的 Bug 已解决
- [ ] 相邻功能未受影响：[列出验证的功能]
- [ ] 边界情况已覆盖：[列出验证的边界]
```

### 教训案例

> **典型回归案例**：修复模块 A 的排序逻辑（Bug X），导致模块 B 的渲染错位（Bug Y）。
> **根因**：修复时修改了共享工具函数的排序逻辑，影响了所有使用该函数的场景，而非仅目标场景。
> **教训**：修改共享逻辑时，必须验证所有使用该逻辑的场景。

## 3. 决策回溯

### 触发条件

当发现之前的设计决策有误时：

- 实施后发现方案不可行
- 新需求与已有决策冲突
- 性能/体验不达标需要换方案

### 回溯流程

```
发现问题 → 记录废弃原因 → 更新 DECISIONS.md → 修改代码 → 更新 SPEC（如需）
```

### 详细步骤

1. **记录废弃原因**：在 DECISIONS.md 中将原决策标记为 `[SUPERSEDED]`，说明为什么废弃
2. **新增替代决策**：用 ADR 模板记录新方案
3. **修改代码**：按新方案实施
4. **更新 SPEC**：如果决策变更影响需求描述，同步更新 SPEC

### 反模式

- ❌ 直接改代码不记录为什么废弃原方案
- ❌ 删除原决策记录（应保留追溯）
- ❌ 新方案不做 ADR 记录

## 4. 实验性代码管理

### 触发条件

用户说"先试试"、"先这样看看效果"等探索性指令时。

### 管理流程

```
标记实验 → 实施 → 验证 → 固化或回滚
```

### 标记规范

在代码中添加注释标记：

```javascript
// EXPERIMENTAL: [描述] — 待验证后决定保留或回滚
```

在 CLAUDE.md 中记录：

```markdown
### MARK #N: 实验性代码 — [描述]

- 内容：[文件:位置] 的 [功能] 为实验性实现
- 状态：待验证
- 后续：验证通过则移除标记；不通过则回滚
```

### 验证后处理

| 验证结果 | 动作                                            |
| -------- | ----------------------------------------------- |
| 通过     | 移除 `EXPERIMENTAL` 注释，MARK 状态改为"已固化" |
| 不通过   | 回滚代码，MARK 状态改为"已废弃"，changelog 记录 |
| 部分通过 | 保留有效部分，回滚无效部分，分别记录            |

### 反模式

- ❌ 实验性代码不标记就合入
- ❌ 验证后忘记移除标记或回滚
- ❌ 不在 CLAUDE.md 中记录实验状态

---

## 轻量验收场景格式

对于关键需求，使用轻量验收场景描述（比纯文字更容易验证，比完整 EARS 更轻量）：

```markdown
### 需求：[需求名称]

WHEN [触发条件]，
系统 SHALL [预期行为]。

#### 验收场景：[场景名]

- 前置：[初始状态]
- 操作：[用户操作]
- 预期：[期望结果]
```

**示例**：

```markdown
### 需求：并发节点嵌套模板

WHEN 并发节点的分支引用了模板，
系统 SHALL 正确展开模板内部节点并计算包围框。

#### 验收场景：正常嵌套

- 前置：模板 A 包含 3 个节点
- 操作：在并发节点分支中引用模板 A
- 预期：模板展开后，分支包围框正确包含所有子节点
```
